# 14 — TCS2 (Tick Collection Service)

**STATUS: DRAFT — design in discussion 2026-09-19/20. No code. Points only.**

## Purpose
- One system that listens to Dhan ticks and serves them to whatever needs them.

## Decisions locked
- **D1** — TCS2 and TFA are **mutually exclusive**. TFA's own code/WS path is
  untouched; it simply is not run.
- **D10** (2026-09-23) — **TCS2 is the only program that runs.** TFA is not run
  at all.
  - **Connections: 4 of 5** — one per instrument process (D9). See the budget
    in D9.
  - The per-connection cap **is** in our code:
    `DHAN_WS_MAX_INSTRUMENTS_PER_CONN = 5000` in
    `server/broker/adapters/dhan/constants.ts`, and `subscriptionManager.ts`
    budgets against it. Dhan signals a breach with disconnect code 804,
    "Instruments exceed limit". **475 is what we have proven live**; 5,000 is
    Dhan's documented figure.
  - Every instrument fits inside one connection, the largest (banknifty, ~1,459)
    using under a third of the 5,000.
- **D2** — TCS2 is **not** a TFA replacement. Its own jobs. On a TCS2 day,
  TFA's outputs (live features for SEA/blast) simply are not produced.
- **D4 — REVISED 2026-09-23: ALL FOUR instruments.** The earlier "NIFTY 50 only"
  is withdrawn (Partha). **One program, run once per instrument**, as in D9.
  What differs per instrument is config, not code — see D11.
  - Consequence: nothing goes dark on a TCS2 day. blast's crude paper runner
    keeps its data.
- **D5** — listen to the **WHOLE option chain**, every strike, both sides, on
  **every expiry that instrument has** (3 for nifty, 2 for the rest — D11).
  Not a moving band around the money.
  - Reason: a band has to follow price through the day, so a position built at a
    far strike is invisible until the market drifts there. Points 12 and 13 are
    about positioning moving BETWEEN strikes — a window that moves with price
    could mask the very thing being looked for.
  - Cost is fine: Dhan allows 5,000 contracts per connection; raw ticks are not
    stored, so there is no disk cost.
- **D7** — **TCS2 stands alone. It does not depend on the API server.**
  - Its own Dhan login and its own contract list (detailed scrip master).
    **No chain fetch at all** — see D12; the chain is built from ticks and IV is
    computed. Needs its own copy of the credentials.
  - Reason: 2026-09-18 the server went down at 09:59 and TFA lost the option
    chain for all four instruments while its own Dhan price feed kept running.
    The thing everything depends on must not itself depend on a program that is
    restarted regularly.
- **D3** — listens to **option, index, futures and India VIX** ticks.
  - options = primary for the 15 rules
  - index = price, strikes, settlement (arrives as price only — no volume/book)
  - futures = supporting; **and the only underlying for crude/gas (no MCX index)**
  - VIX = volatility regime — **NSE only**; no crude/gas equivalent exists

- **D11 — per-instrument capability table (2026-09-23).** Measured from our own
  recordings on 2026-09-22, not from documentation:

  | | nifty50 | banknifty | crudeoil | naturalgas |
  |---|---|---|---|---|
  | spot index | yes | yes | **none** | **none** |
  | futures | yes | yes | yes, **is** the underlying | yes, **is** the underlying |
  | India VIX | yes, real | same VIX, borrowed | **meaningless** | **meaningless** |
  | weekly options | yes (Tuesday) | **no, monthly only** | **no, monthly only** | **no, monthly only** |
  | chains to watch | 3 (week/month/next) | 2 (month/next) | 2 | 2 |
  | strikes / legs per chain | 236 / 472 | 364 / 728 | 207 / 414 | 92 / 184 |
  | strike spacing | 50 | 100 (500/300 far out) | 50 | 5 |

  - Proof banknifty has no weeklies: on 2026-09-22 the nearest nifty expiry was
    **that same day**, the nearest banknifty expiry **2026-09-29** (month end).
  - TFA writes a `*_vix_ticks` file next to crude and gas too (~207 KB/day). It
    is the same India VIX instrument; for MCX it carries no information. TCS2
    should not subscribe it for crude/gas.
  - **S3 (current week) does not exist for banknifty, crude or gas.** Spec 15's
    points that compare across week/month/next (13, and the weekly half of 11/12)
    reduce to two expiries for three of the four instruments.
  - Totals if all four run: ~4,070 option legs plus futures/index/VIX. Past the
    475 proven on one connection, so expect **one connection per instrument**
    (4 of the 5 slots) or a split within an instrument for banknifty.
  - On MCX the options are written on a **futures contract**, and option expiry
    is a few days **before** the futures expiry it belongs to (crude options
    2026-10-15 on OCT FUT 2026-10-19). Pair them from the detailed scrip master,
    not by assuming the dates match.
  - **T191 corrected:** TFA already pairs all four correctly. The real MCX bug is
    a **frozen `spotPrice` in the chain snapshots** — 324 crude snapshots on
    2026-09-22, one single value. TCS2 avoids it by taking spot from the futures
    tick stream (D12).

- **D12 — the option chain is BUILT FROM TICKS, not fetched (Partha 2026-09-23).**
  TCS2 never calls Dhan's option-chain API. It subscribes every leg and assembles
  the chain itself from the tick stream.
  - **This works — the ticks carry everything the chain shows except IV.**
    Verified in the 2026-09-22 recordings, each option tick has: `ltp`, `oi`,
    `high_oi`, `low_oi`, `volume`, `atp`, `bid`/`ask` + sizes, 5-level `depth`,
    `total_buy`/`total_sell`, `day_open/high/low/close`, `ltq`, `ltt`, `strike`,
    `opt_type`.
  - **What must be computed instead of received:**
    - **IV** — the only chain field not in the tick stream. Black-Scholes implied
      vol from premium, spot, strike, time to expiry, r. The BS code already
      exists in `claude_cohort`.
    - **OI change** — from our own previous snapshot, not from Dhan.
  - **What must come from the scrip master:** the strike list, each leg's security
    id, lot size, tick size, and the weekly/monthly flag. Use Dhan's **detailed**
    master `api-scrip-master-detailed.csv`, not the compact one the server uses —
    it adds `UNDERLYING_SECURITY_ID` (26000 NIFTY, 26009 BANKNIFTY, 294 CRUDEOIL,
    401 NATURALGAS) and `EXPIRY_FLAG` (M/W), so legs group by id instead of by
    parsing symbol strings.
  - **Spot comes from the tick stream too** — the index tick for nifty/banknifty,
    the futures tick for crude/gas. This sidesteps T191's frozen MCX spot.
  - Why it matters beyond independence: a fetched chain is a snapshot every N
    minutes; a built chain is current on every tick, which is what points 11 and
    12 need.

- **D14 — total isolation between instrument processes (Partha 2026-09-23).**
  The tick analyser for an instrument runs **inside that instrument's process,
  alone**. No process shares ticks, chain state or analyser state with another.
  - **Shared code is fine; shared state is not.** All four run the same modules,
    imported as a library. What is forbidden is a common store, queue, cache or
    analyser instance that two instrument processes both touch.
  - Each process owns its own chain, its own rolling state, its own files, its
    own config.
  - **India VIX is subscribed twice** — once by nifty50, once by banknifty — on
    two different connections, rather than fetched once and shared. That is the
    rule working as intended: 1 leg each out of 5,000. TFA already does this,
    writing four separate `*_vix_ticks` files.
  - **What this costs, stated plainly:** nothing cross-instrument can be computed
    inside TCS2 — no nifty-vs-banknifty divergence, no crude-vs-gas correlation,
    no "NSE is risk-off so treat the MCX signal differently". If we want those
    later they belong in a **downstream consumer** reading the four processes'
    outputs, never in a shared analyser. Worth it: isolation is what keeps one
    instrument's bad day from taking the other three with it, which is exactly
    what T186 and the 2026-09-18 corruption did.

- **D15 — each process has its own screen (Partha 2026-09-23).** One instrument =
  one process = one screen. Four processes, four screens, as the per-instrument
  chart windows already work.
  - **This dissolves the "how do consumers get the data" question for the screen.**
    Nothing has to be delivered anywhere: the screen that shows an instrument is
    attached to the process that holds that instrument's ticks, chain and
    analyser state. No files to tail, no sockets, no shared store, and D14 is
    kept without effort.
  - **Consequence for spec 12:** today's screen is one window with a 2x2 grid,
    one quadrant per instrument. That becomes **four windows, each showing one
    instrument full-screen** — which is what spec 15 §5.7 already drew for nifty
    (rules panel, decision box, strike ladder, levels/migration). The four
    windows can sit on different monitors.
  - **Settled by D16: the screen runs inside the process.**
  - Job 3 ("share live ticks with other programs") therefore no longer has the
    screen as its driver. What remains of it is the SEA/blast question below.

- **D16 — the screen runs INSIDE the instrument process (Partha 2026-09-23).**
  One process per instrument, containing feed, chain, analyser, recorder and
  screen. Not eight processes.
  - Claude recommended a separate screen process; Partha chose same-process.
    Recorded so the reasoning is not relitigated.
  - **The arrangement that makes this safe, and it is not optional:**
    - **Tkinter on the MAIN thread** (required on Windows), **ticks and the
      recorder on worker threads.** That way a slow or frozen redraw cannot stop
      the feed — a blocked Tk mainloop releases the GIL, so the workers keep
      running.
    - The GUI **never touches the tick path**. It reads an immutable snapshot on
      a timer; the tick thread publishes snapshots and never waits on the GUI.
    - Bounded queues. **If the GUI falls behind, GUI updates are dropped —
      never ticks, never writes.**
    - The recorder gets its own thread, so a slow disk cannot stall the feed
      either.
  - **A heartbeat per thread, reported independently.** The feed, recorder and
    GUI each prove they are alive on their own. The failure this guards against
    is precisely T186 and 2026-09-18: a screen that looks fine while the
    recording behind it stopped hours ago.
  - **Accepted risk:** a hard crash in the GUI takes the feed and recorder with
    it, which would not happen with two processes. The heartbeats make it loud
    rather than silent, which is the part that actually cost us before.

- **D17 — health is shown ON SCREEN only; Telegram comes later (Partha 2026-09-23).**
  Each window shows its own process's three heartbeats (feed, recorder, GUI).
  No alerting to yow-partha in v1.
  - Claude recommended screen + Telegram; Partha chose screen only for now.
  - **Build it so Telegram is a subscriber, not a rewrite.** Health is a small
    structured object the process updates — per-thread last-beat, tick rate,
    last write, current staleness. The screen is one consumer of it. Adding a
    Telegram consumer later must not mean touching the health logic.
  - **Also write the health object to a file each interval**, even in v1. It
    costs nothing, and it is the difference between knowing *when* a process
    stopped and guessing. T186 is still unsolved partly because we have no such
    record for 2026-09-18.
  - **The gap this leaves, stated plainly:** an unattended stop goes unnoticed.
    MCX runs to 23:30 and NSE processes idle after 15:30; nobody is watching a
    screen then. On 2026-09-18 the recorder stopped at 10:00 and it took 2.5
    hours to notice *with* someone at the desk. So the screen must make
    staleness impossible to miss rather than subtle — the existing 60-second
    stale rule and last-updated clock in `market_screen` are the right shape,
    and the health row belongs at the top of the window, not the bottom.

- **D18 — scheduled tasks start them, the launcher inspects and restarts
  (Partha 2026-09-23).** Same split that already works for yow-partha: a
  Windows task gets it running without anyone at the desk, and the launcher is
  how it is watched and controlled afterwards.
  - **Four tasks**, named like the existing ones
    (`Lubas-YowPartha-Daily`, `Lubas-CB2-Tracker-Daily`):

    **All four start at 08:54** (Partha 2026-09-23), matching the existing
    `Lubas-YowPartha-Daily` 08:55 slot so the machine is woken once.

    | task | instrument | legs | market opens | warm-up | runs until |
    |---|---|---|---|---|---|
    | `Lubas-TCS2-Crudeoil-Daily` | crudeoil | 829 | 09:00 | 6 min | 23:30 |
    | `Lubas-TCS2-Naturalgas-Daily` | naturalgas | 369 | 09:00 | 6 min | 23:30 |
    | `Lubas-TCS2-Nifty50-Daily` | nifty50 | 1,419 | 09:15 | 21 min | 15:30 |
    | `Lubas-TCS2-Banknifty-Daily` | banknifty | 1,459 | 09:15 | 21 min | 15:30 |

  - **The warm-up fits, and it falls the right way round.** Each process must
    download the detailed scrip master (~35 MB), build its strike list and
    subscribe its legs at 100 instruments per message — 15 messages for
    banknifty. The two with only 6 minutes are the **smallest** (829 and 369
    legs, 9 and 4 messages); the two large ones get 21 minutes.
  - **One shared scrip-master file, downloaded once.** Four simultaneous 35 MB
    downloads at 08:54 is waste, and the file is identical for all four. A
    read-only cached file on disk is **not** a D14 violation — D14 bans shared
    analyser and tick state, not reading the same config. Rule: use the cached
    copy if it is less than 24 hours old, otherwise download. First process up
    downloads; the rest read.
  - **Launcher gets a TCS2 section:** the four processes with their D17 health,
    and start / stop / restart per instrument. Restarting one must not touch the
    other three (D14).
  - **Stopping is the unsolved half.** NSE processes should stop after 15:30 and
    MCX after 23:30, but *how* they stop depends on the deferred crash-safe
    recording decision — a graceful stop that closes the file cleanly is a
    different thing from being killed by the scheduler. **Do not wire an
    automatic stop until that is settled.** A mid-session restart is what
    corrupted the recordings on 2026-09-18.

## Expiry scope — SETTLED by spec 15 (2026-09-23), widened to four instruments
- **nifty50:** S1 index, S2 futures, VIX, and **three** chains —
  S3 current-week, S4 current-month, S5 next-month. ~1,416 legs.
- **banknifty:** S1 index, S2 futures, VIX, and **two** chains (month, next).
  No weekly exists. ~1,456 legs.
- **crudeoil / naturalgas:** **no index, no VIX**, futures **is** the underlying,
  and **two** chains (month, next). ~828 / ~368 legs.
- S4/S5 are **not recorded today for any instrument**; TCS2 job 5 is what
  creates them.
- Which futures: pair option expiry to futures contract via the detailed scrip
  master. On MCX they differ by days (crude options 10-15 on OCT FUT 10-19).

## Jobs (proposed, not yet confirmed)
1. Listen — options, index, futures, VIX
2. Record safely — no silent stops, no corrupt files
3. Share live ticks with other programs — **the screen no longer needs this
   (D15); only SEA/blast might**
4. Find strikes from Dhan's detailed scrip master — **settled, D7 + D12**
4b. Build the option chain from the ticks, computing IV — **settled, D12**
5. Cover more expiries — week + month + next month — **settled, see Expiry scope**
6. Watch its own health — tick rate, stalls; **shown on screen, D17**
7. *(later)* Replay a recorded day

## Storage — D6 positioning lifecycle (2026-09-23)
- **Capture positioning for ALL strikes, ALL three expiries, from the contract's
  START and continuing until it expires / rolls over.** Not a rolling window.
- Why: points 5-8, 11, 12, 13 are about big players building over days and moving
  between strikes and expiries. That story only exists if each contract's whole
  life is kept.
- What: chain snapshot rows — OI, OI change, premium, volume, IV per strike per
  side — at end of day plus every 15 min intraday.
- Size: ~1,400 rows per snapshot x 25 snapshots/day = a few MB/day. Raw ticks
  were 2.2 GB/day.
- Two ways to get "since start":
  1. forward from the day TCS2 starts
  2. **backfill from Dhan's historical API — TESTED 2026-09-23:**
     - **works, including for a contract that expired yesterday.** 23300 CE
       (expiry 09-22) returned its whole life: OI 65 on 09-01 -> 3,889,340 on 09-21
     - **old expiries return nothing** - a 2026-06-16 contract gave 0 candles.
       Dhan keeps recent expiries only; the cutoff is not yet found
     - **intraday 5-min candles carry OI too** - 231 candles over 09-18..09-22,
       better than daily
     - **BUT the two endpoints disagree.** For 23300 CE on 09-18, against our own
       recorded chain snapshot:
       | source | OI |
       |---|---|
       | our recording 09:15 -> close | 6,604,520 -> 8,520,590 |
       | Dhan intraday history | 8,061,170 |
       | Dhan daily history | 3,889,340, *identical on 09-21 and 09-22* |
       Intraday is in the right range; daily is less than half and repeats
       across days - looks stale. **Validate against our 81 days of recorded
       snapshots before relying on either.** See T189.
- We already hold **81 days of near-expiry chain snapshots** from TFA; those can
  be imported so past weeklies keep their final-week history.

## Storage — D8 raw ticks ARE stored (2026-09-23, reversing the earlier "live only")
- **TCS2 stores raw ticks.** Reason: with the analysis inside TCS2 and no
  recording, a change to the analysis could never be tested - there would be
  nothing to replay it against. Everything useful found this month (the flow
  study, the backtests, the futures-vs-options comparison) came from raw ticks
  being on disk.
- Size, **all four instruments**: measured 2026-09-22 with one chain each,
  compressed option ticks were nifty 174 MB, banknifty 144 MB, crude 131 MB,
  gas 29 MB = **478 MB/day**. Month and next-month chains trade far less, so
  adding them lands near **1 GB/day**. 330 GB free -> roughly **1 year**.
- **Must not repeat T185/T186:** a recorder heartbeat so a silent stop is caught,
  and files that survive a crash. `_shared/gz_reader.py` already reads past a
  corrupt member; the writing side needs the same care.

## D9 — one process per instrument, analysis INSIDE (2026-09-23, reaffirmed)
- **Confirmed by Partha 2026-09-23: each instrument runs in its own process.**
  Four processes: nifty50, banknifty, crudeoil, naturalgas. Same program, four
  configs.
- Matches TFA's proven shape; the launcher already handles per-instrument processes.
- Points 12/13 compare strikes and expiries, so keeping all of one instrument's
  contracts in one program beats shipping state between two.

**Connection and instrument budget** (legs from D11; cap 5,000/connection):

| process | chains | option legs | plus | total | connections |
|---|---|---|---|---|---|
| nifty50 | 3 | 1,416 | index + futures + VIX | 1,419 | 1 |
| banknifty | 2 | 1,456 | index + futures + VIX | 1,459 | 1 |
| crudeoil | 2 | 828 | futures | 829 | 1 |
| naturalgas | 2 | 368 | futures | 369 | 1 |
| | | **4,068** | | **4,076** | **4 of 5** |

**D13 — one connection per process, always (Partha 2026-09-23).** A process
never opens a second connection. It does not need to: 5,000 securities fit on
one, and the largest instrument asks for 1,459. This is a design rule, not a
budget that gets recalculated — if an instrument ever looks like it needs a
second connection, that is a bug or a wrong strike list, not a reason to split.
One of the five account slots stays spare.

**Why separate processes matter here beyond convention:**
- **Different market hours.** NSE runs 09:15-15:30, MCX 09:00-23:30. One process
  per instrument means crude and gas keep running after the NSE pair have shut
  down, instead of one long-lived process spanning both.
- **Independent restart.** A restart to fix one instrument does not interrupt the
  other three. T186 (recorder stopped silently) and the 2026-09-18 corruption
  both came from a process-wide event.
- **Isolation of a bad day.** A crash or a corrupt write is contained to one
  instrument's files.

- **Condition:** thresholds and parameters live in config the program re-reads
  while running, so tuning does not restart the feed. A mid-session restart is
  what corrupted the recordings on 2026-09-18.

## Constraints
- Dhan: **5 WS connections per account**. Secondary is 5/5 (4 TFA + 1 AI Live).
  → TCS2 can only run when TFA does not.
- API server dependency is what broke on 2026-09-18 — job 4 removes it for strikes.
- Disk: 191 GB used by raw ticks (~85 days), 330 GB free → **~7 months at today's rate**.

## Facts measured (2026-09-17/18)
- TFA subscribes the **whole chain**, both sides: nifty 472 legs, banknifty 728,
  crude 414, gas 184. Not a window.
- Option ticks by distance from spot: ±3 = 9%, ±10 = 31%, ±20 = 61%, ±40 = 93%.
- Futures run **+20 to +33 pts** over spot near expiry (+88 earlier in the cycle);
  **weekly options price around spot, not futures**.
- Index (spot, id 13) is ticker-mode only: no volume, no OI, no book.
- Option ticks DO carry full order flow — bid/ask, size, depth, OI.

## Open questions
- **Crash-safe recording — the mechanism, not just the requirement — DEFERRED
  by Partha 2026-09-23, discuss later.** Three options were put and none chosen:
  (a) keep gzip and fix the reading side, which `_shared/gz_reader.py` already
  does but only rescues data after the fact; (b) flush and close a gzip member
  every N seconds so a crash loses only the last member; (c) write plain NDJSON
  and compress at end of day — safest, but ~10 GB/day uncompressed on disk
  mid-session and one end-of-day step that can itself fail.
  Claude's recommendation was (b) plus (a). Context: T185, where a corrupt
  member blocked every reader, hit 16 of 326 recordings, some losing 99.9% of
  the day.
